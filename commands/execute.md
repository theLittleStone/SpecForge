description: 执行命令——以 T/C 双视角交叉循环处理当前活跃工作项（写测试→对侧验收→写实现→对侧验收→分层验证→人工确认），可选 auto / step 模式

## 功能说明

取代原 test-generate / code-generate / test-verify / code-review 四个命令，是执行侧的唯一入口。

执行不再是「规格 → 测试 → 代码 → 验证 → 审查」的固定流水线，而是**工作项驱动的 T/C 双视角交叉循环**：

- **T 视角（Test Agent）**：只信任规格。撰写测试与 Test Double，自证 RED；**验收 C 的产物**（验证 GREEN + 审查实现）。
- **C 视角（Code Agent）**：只信任测试。复现 RED 并审查测试（**验收 T 的产物**）；撰写实现（假设驱动，Attempt Log 记录）。
- 任何一方的产物都由**对侧**验证与判定——没有独立的审查者，也没有自我评价。
- 失败按 AGENTS.md §失败路由协议（三分类 + 对侧判定 + 动态预算）处理；失效与回退按 §统一失效协议 与规划阶段对齐。
- 用户保留终审：`[人工]` 项、判定争议、L3 强制路由、工作项 DONE 确认。

两种模式：

- **auto**：全程自主推进（预算与守卫内），仅在介入点暂停交还用户
- **step**：每个视角动作完成后暂停展示产物，等待用户确认继续（替代原手动命令链的精细控制）

## 行为规则

执行流程：

0. 检查项目根目录 `AGENTS.md` 已包含工作流共识（含「失败路由协议」「统一失效协议」「轻量 spec 规则」节）；若缺失，醒示用户先运行 `/setup` 初始化并终止
1. 读取 `planning/plan.md` 与 `planning/specs.md`
2. 确定处理对象：当前活跃工作项（首个「Depends On 全部 DONE」的 TODO/ACTIVE 工作项）
3. 若活跃工作项为 TODO → 先按 `/specify` 流程展开（展示规格预览 → 用户确认 → 写入 specs.md，工作项状态 → ACTIVE）；specify 判定工作项过大时拆分子工作项回写 plan.md（运行时分解）
4. 按规格状态推进该工作项的全部规格（见 §状态路由），每个规格按顺序经 T → C → T 交叉循环
5. 全部规格终态后执行跨 spec 自查 → 输出工作项总结 → 用户确认 → 工作项标记 DONE

### 状态路由（规格推进）

| 规格状态 | 动作 | 完成后状态 |
| --------- | ------ | ----------- |
| `[新增\|修改: 已定义]` | T 视角写测试 | `[测试中]` |
| `[新增\|修改: 测试中]` | 继续 T 视角（中断恢复） | `[测试中]` → 自证 RED 后待 C 验收 |
| `[新增\|修改: 测试已验收]` | C 视角写实现（Attempt Log） | `[实现中]` |
| `[新增\|修改: 实现中]` | 继续 C 视角（中断恢复） | `[实现中]` → 待 T 验收 |
| `[新增\|修改: 已验收]` | T 视角分层验证 L2/L3 + [人工] 项 → 用户确认 | `[已验证]`（终态） |
| `[新增\|修改: 待修复]` | 按 §失败处理 分类路由 | 按路由结果 |
| `[新增\|修改: 已验证]` | 跳过，处理下一规格 | — |
| `[废弃: 待删除]` | C 视角解引用（grep 实测依赖者 + 移入 `_deprecated/`）→ 验证清单 | `[废弃: 已解引用]` |
| `[废弃: 待修复]` | 按 §失败处理 分类路由 | 按路由结果 |
| `[废弃: 已解引用]` | 跳过 | — |

### T 视角：写测试（RED）

1. 读取规格（Spec / Interface / Test Double / Test Cases）+ `style_guide.md`（缺失时调 style-resolver 生成；轻量/废弃规格跳过）
2. 依据 Test Cases 撰写测试：
   - `[自动化]` 条目按双轨落地——**F2P**（问题验证，断言新行为，基态必须 FAIL）/ **P2P**（回归保护，断言既有行为，基态必须 PASS）；每非轻量规格至少 1 个 F2P 自动化测试
   - 引用符号必须已在 Interface 段定义（禁止引用未定义符号）
3. 开放边界 → 自建 Test Double（stub / fake），测试不依赖实现细节
4. 执行测试**自证 RED**：F2P 全部失败且失败于**断言**（编译/加载/运行错误不算 RED）——RED 确认是硬关卡，意外 PASS 或 error 不得推进
5. 顺带执行 P2P 相关既有测试，确认基态 PASS（不破坏既有行为）
6. `[人工]` 条目组装为验证清单（操作 / 预期 / 通过标准）
7. 规格状态 → `[测试中]`；完成后等待 C 视角验收

### C 视角：复现 RED + 审查测试（对 T 产物的验收）

1. 执行测试**复现 RED**：确认失败于断言而非测试自身错误
2. 静态审查测试质量（test-hacking 红名单，发现即分类路由，不修改测试）：
   - 直接修改测试文件 / 跳过或禁用用例 / 弱化断言 / 修改 fixture
   - 操纵环境或测试运行器配置 / 固定或放宽依赖版本 / 添加环境变量
   - 测试专属逻辑 / 为实现通过而改变被测行为 / 硬编码输出 / 魔法常量取自测试
3. 判定：
   - 测试有效 → 规格状态 `[测试已验收]`
   - 测试缺陷 → Issues 记 `[测试缺陷]`（对侧判定），退回 T 视角认领重写（重写 ≤ 2 次，见 §失败处理）

### C 视角：写实现（GREEN，假设驱动）

1. 读取规格（含「上游变更因果链」段——上游 API/数据结构变更时理解「为什么改」）+ 已验收测试
2. **骨架优先读代码**：Affected Files 的相关符号声明头 + 相关行，禁止无证据扩大上下文
3. **假设声明**：基于测试预期提出实现假设（为什么这么做、预期如何满足测试）
4. 实现：
   - 满足全部 F2P 与 P2P 的期望行为；不修改测试代码；Affected Files 不得含测试目录路径
   - **「无需修改」声明路径**：判定契约已满足 → 声明无需修改，直接进入 T 视角验证（不产 diff）
   - diff 应用失败（context 失配）→ 只修 context 不重写内容
5. Attempt Log 写入（C 填假设与补丁摘要；结果/证据/诊断由 T 回填）
6. 规格状态 → `[实现中]`；完成后等待 T 视角验收

### T 视角：验证 GREEN + 审查实现（对 C 产物的验收）

1. 执行测试：全部 F2P 通过 + 全部 P2P 通过 → GREEN
2. 审查实现（反模式清单，发现即分类路由）：
   - RepeatedView / ZoomOut / OverlyDeepZoom / Scroll（低效导航与探查）
   - UnresolvedRetry（无进展重试）/ EditReversion（回退先前成功编辑）/ StrNotFound / NoEffectEdit / AmbiguousTarget
   - 为满足测试而特判（测试专用分支、硬编码）——影响盲区：修复了目标但未更新下游依赖者
3. 判定（判定权在 T）：
   - 通过 → 回填 Attempt Log 结果/证据/诊断 → 规格状态 `[已验收]`
   - 失败 → 分类 Issues + 回填 Attempt Log → 按 §失败处理 路由

### 分层验证（规格 `[已验收]` 后）

按变更类型定深度（深度取自 plan.md §变更分类规则表的「验证深度」列）：

| 层 | 内容 | 执行 |
| ---- | ------ | ------ |
| L1 | 规格测试（F2P + P2P） | GREEN 验收时已执行 |
| L2 | 相关文件测试（Affected Files 内相关文件既有测试） | `[已验收]` 后自动附带 |
| L3 | 影响范围回归（工作项 Affects 相关文件 + 依赖链） | 工作项最后一个规格验收后执行 |
| L4 | 全量回归 | progress-report 收尾 |
| L5 | 行为合理性（[人工] 项 + 交叉审查） | [人工] 引导用户执行，结果回写 |

- 内部实现 → L1-2；API 签名变更 / 数据结构变更 → L1-3；纯新增 → L1-2；纯删除/废弃 → L1-3（含 grep 引用扫描）；文档/配置 → 轻量 L1
- 任一 L2/L3 失败 → 按 §失败处理 分类路由（回归破坏优先检查影响范围与上游因果，不得盲目重试）

### [人工] 项落地

按 AGENTS.md §人工验证落地规则：逐项引导用户执行，回写 `✓ PASS` / `✗ FAIL — <备注>`；全部落地且分层验证通过后，展示规格验收摘要 → 用户确认 → 规格状态 `[已验证]`

### 失败处理（对侧判定 + 动态预算）

按 AGENTS.md §失败路由协议：

1. **判定**：对侧视角分类（GREEN 失败由 T 判定 / RED 异常由 C 判定）→ 产出方辩护 → 争议交用户终审
2. **路由**：
   - `[实现缺陷]` → 预算内迭代：L1（首次返工，Debug 报告前置：根因/证据/代码位置）→ L2（二次返工，生成 2-3 个不同策略候选，用户选 1 或按验证规则择优，其余记入负证据）→ L3（三次返工，强制路由 /specify 或 /plan 模式 B）；总 Attempt ≤ 4
   - `[测试缺陷]` → T 视角认领重写（≤ 2 次；第 3 次路由 /specify——测试反复失败提示规格歧义）
   - `[规格缺陷]` → 路由 /specify（统一失效协议：单规格 + Interface 依赖者失效）
3. **振荡检测**：Attempt Log 连续 ≥ 2 次相同诊断 → 跳过 L2 直接 L3
4. **上游溯源**：归因前先检查依赖链上游 API/接口变更——表面报错点可能不是根因点
5. 任何失败方案的 Attempt Log 标记「已试」，同一方案不得原样重试

### 跨 spec 自查与工作项收尾

工作项全部规格 `[已验证]`（废弃规格 `[已解引用]`）后：

1. **C 自检 + T 复核**（交叉审查的收尾）：
   - 跨 spec 一致性（Interface 引用闭合、无重复实现）
   - 影响盲区（修复了目标但漏了下游依赖者——grep 实测）
   - under-generation vs 结构性修（最小改动是否掩盖了结构性缺陷——作 `[人工]` 审查项）
2. 输出**工作项总结**：执行证据（Attempt 次数 / 验证轮数 / 判定争议次数 / 相位序列 PTS 摘要）+ 验收结果 + 遗留 `[人工]` 项
3. **用户确认 → 工作项标记 DONE**（plan.md 更新；工作项边界是终审点，不自动 DONE）

### 守卫（保证终止）

- **循环预算**：每工作项 TDD 循环 ≤ 3-4 次（超出 → 提醒 /plan 模式 B 或 progress-report 提前收尾）
- **实现预算**：Attempt ≤ 4（L0-L3）；**测试重写预算**：≤ 2 次
- **振荡检测**：连续相同诊断 → 直跳 L3
- **停滞诊断**：连续多轮无新证据/无编辑 → 输出「You may be stuck in {phase}」诊断 + 建议运行时分解（拆分工作项回写 plan.md）或 /plan 模式 B
- **三相位守卫**（定位 → 修补 → 验证）：未验证不得 DONE——跳过验证是最高危信号；发现跳过 → 立即补验证并警告

### 运行时分解

执行中发现当前工作项过大（一个 diff 装不下 / 多个独立行为）→ 拆分子工作项回写 `planning/plan.md`（登记 Depends On 与失败路由），逐个展开处理——执行可以修改计划图

## 输入来源

| 文件 | 用途 | 关键内容 |
| ------ | ------ | --------- |
| `planning/plan.md` | 计划图 | 活跃工作项、变更类型（含验证深度）、Depends On / Affects、失败路由、负证据 |
| `planning/specs.md` | 规格库 | 规格契约（Spec / Interface / Test Double / Test Cases）、状态、Issues、Attempt Log |
| 代码库 | 实现与验证 | 测试执行、骨架读取、grep 实测 |
| AGENTS.md | 共识 | 状态机、失败路由协议、统一失效协议、人工验证落地规则、轻量 spec 规则 |

## 输出

推进当前活跃工作项的规格状态（按 §状态路由），维护 Attempt Log 与 Issues，更新 `planning/specs.md` 与 `planning/plan.md`（工作项 ACTIVE → DONE）。

### Markdown 预览（规格验收）

```md
## 规格验收：spec_a（Work Item: W2）

### Attempt Log（最近 ≤ 4）

| # | 假设 | 补丁摘要 | 结果 | 证据 | 诊断 | 下一步 |
|---|------|---------|------|------|------|--------|
| 1 | 采用 xx 方案 | 新增 notify.py + 钩子 | FAIL | F2P-1 断言失败 | [实现缺陷] 事件未触发 | L1：Debug 报告前置 |

### Issues

- [实现缺陷] <详情>（T 判定 / C 辩护：…）

### 分层验证

- L1: 2 F2P + 3 P2P 全过
- L2: 相关文件测试 6 过 0 败
- L3: 影响范围回归 PASS

### [人工] 项

- [ ] 手工检查 xx → ✓ PASS

→ 用户确认后规格 → [新增: 已验证]
```

### Markdown 预览（工作项收尾）

```md
## 工作项总结：W2

- 执行证据：Attempt 2 / 验证轮 5 / 争议 1 / PTS: L5 P2 V3
- 跨 spec 自查：C 自检 ✓（无重复实现、无影响盲区）/ T 复核 ✓
- 遗留 [人工] 项：无

→ 用户确认后 W2 → DONE
```

## 下一步

- 工作项 DONE → 有下一工作项 → 提醒用户运行 `/execute` 继续（或 /plan 模式 B 修订）
- 全部工作项 DONE → 提醒用户运行 `/progress-report` 收尾（L4 全量回归 + 归档）
- `[规格缺陷]` 路由 → 提醒用户运行 `/specify` 重定义

## 约束

- 每次只处理一个工作项，禁止跨工作项执行
- 产物必须由对侧验收：T 不验收自己的测试，C 不验收自己的实现；任何一方不得自我评价
- 实现方永不修改测试代码；测试方永不修改实现代码（只分类路由）
- RED 确认只认断言失败：编译/加载/运行错误不算 RED
- 未验证不得标记 DONE（三相位守卫）；跳过验证必须立即补验
- Attempt ≤ 4 / 测试重写 ≤ 2 / TDD 循环 ≤ 4，超限必须路由，禁止盲目重试
- 失败方案标记「已试」，同一方案不得原样重试（负证据）
- 轮内禁止 git 提交；git restore 仅在用户要求或代码严重污染时执行（AGENTS.md §统一失效协议）
- `[人工]` 项结果未落地，规格不得推进到 `[已验证]`
- 写文件前必须展示预览并等待用户确认（auto 模式下干预点：规格展开、候选选择、L3 路由、[人工] 项、工作项 DONE）
