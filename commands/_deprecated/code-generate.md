## 功能说明

该命令是 TDD 流程的第三步（GREEN 阶段），在 test-generate（RED 确认）**之后**执行。

核心原则：**先读测试，再写代码**。agent 必须阅读每个 spec 的测试代码，理解测试断言与行为期望，然后生成实现代码使 `[自动化]` 测试通过，并引导用户完成 `[人工]` 测试。

若 spec 声明了 Test Double，agent 需理解生产实现与 Test Double 共享同一 Interface，通过依赖注入切换。

支持的操作类型：

- **新增**：根据测试代码，创建新代码文件或添加新代码。若存在 Test Double，同时生成生产实现
- **修改**：根据测试代码的回归保护，修改现有代码
- **废弃**：按 `Depended By` 解引用后移入 `_deprecated/`（不直接删除），验证通过后由 progress-report 收尾统一物理删除
- **轻量**：无测试代码可依据，按 `Spec` 与 `Interface`（如有）直接实现，验收交给 `/test-verify` 轻量验收

实现约束：本命令只写实现代码，**永不修改测试代码**——疑似测试错误只能按 AGENTS.md §失败路由协议 分类路由到 `/test-generate`。

## 行为规则

执行流程：

0. 检查项目根目录 `AGENTS.md` 已包含工作流共识（含「失败路由协议」与「人工验证落地规则」节）；若缺失，醒示用户先运行 `/setup` 初始化并终止。读取 `./style_guide.md`。如不存在，调用 `style-resolver` skill，从项目配置自动生成代码风格规范，经用户确认后写入，再继续后续流程
1. 读取 `planning/specs.md`
2. 读取 `planning/plan.md`，获取 `# Goal`、`# Scope` 与该工作项的变更类型/描述/设计引用作为背景上下文
3. 选择处理对象：
   - `[新增|修改: 测试已生成]`、`[废弃: 待删除]`、`[新增|修改|废弃: 待修复]`
   - 轻量 `[新增|修改: 已定义]` 规格（跳过测试生成，直接实现）
   - 仅处理 `Issues` 类型为 `[实现缺陷]` 或无 Issues 的 `[新增|修改|废弃: 待修复]` 规格；`[测试缺陷]` / `[规格缺陷]` 类型不属于本命令（见「待修复规格的处理」）
4. 逐 spec 处理（垂直切片——每个 spec 完成实现和全部验证后，再处理下一个 spec）：

   a. **读取测试代码**：从该 spec 的 `Affected Files` 字段获取测试文件路径和 Test Double 文件路径（如有），
       读取测试代码，理解测试框架、断言逻辑和期望行为。同时读取 spec 的 `Interface` 字段确认公共接口契约。
       若 spec 有 Test Double，理解 Test Double 的行为约定，确认生产实现与 Test Double 共享同一 Interface。
        对于 `[新增|修改|废弃: 待修复]` 状态，额外读取 `Issues` 字段了解上次失败原因（含失败类型分类）。
       废弃规格无测试代码，改为读取 `Spec` 与 `Depended By` 定位待删目标及其引用方。
       轻量规格无测试代码，改为读取 `Spec` 与 `Interface`（如有）理解期望行为

   b. **意图说明实现逻辑**：向用户说明——当前 spec 要解决什么问题、实现思路与设计决策、
       涉及哪些源文件、与 Test Double 的关系（如有）

   c. **生成实现代码**：根据操作类型分叉：
      - **新增**：根据测试断言 + `Interface` 契约，生成新代码。
        若 spec 有 Test Double，同时生成生产实现（二者共享 Interface，通过依赖注入切换）
      - **修改**：读取 `Spec` 中指定的现有代码文件，生成 diff 修改方案
      - **废弃**：按 `Spec` 与 `Depended By` 定位待删目标及其引用方，生成三步方案：
         1. **解引用**：修改 `Depended By` 中所有引用方，移除对目标代码的引用
         2. **移动**：将目标代码移入项目根目录 `_deprecated/`，并从构建/测试配置中排除（排除结果由用户人工确认）
         3. **引用同步**：同步更新 `planning/specs.md` 中相关规格的 `Depended By` 字段与 `planning/plan.md` 工作项的 `Affects`（以 grep 实际引用扫描为准），保持与代码一致
         若 `Spec` 未明确指定目标文件/函数，醒示用户确认操作对象，禁止自行搜索删除
      - **轻量**：按 `Spec` 与 `Interface`（如有）直接实现；无测试期望约束，以实现目标为准

   d. **展示 diff 预览**：输出代码差异，等待用户确认。用户提出修改意见 → 回到 c 修订。确认后写入源文件。
       写入后标记状态为 `[新增: 已实现]` / `[修改: 已实现]`（废弃规格标记 `[废弃: 已解引用]`），
       将引用方文件、目标代码原始路径与 `_deprecated/` 内移动后文件路径追加写入 `Affected Files`

   e. **[人工] 测试执行与落地**（仅在 spec 的 `Test Cases` 含 `[人工]` 条目时触发）：
      - 从 spec 的 `Test Cases` 中提取所有 `[人工]` 条目
      - 逐项展示结构化 checklist：操作 / 预期 / 通过标准
      - 提示用户执行并反馈结果（PASS/FAIL）
      - **结果落地**：按 AGENTS.md §人工验证落地规则，将每项结果回写 spec 的 Test Cases 对应条目——通过追加 `✓ PASS`，失败追加 `✗ FAIL — <失败备注>`（含用户反馈）。结果未落地，状态不得推进
      - 全部 PASS 且已落地 → 进入步骤 f
      - 存在 FAIL → 按 AGENTS.md §失败路由协议 判定 Issues 类型（默认 `[实现缺陷]`，附用户反馈详情），状态更新为 `[新增|修改|废弃: 待修复]`，递增 Retry Count，醒示用户「人工测试未通过，已标记为待修复」，**立即停止**

   f. **调用 /test-verify**：
        - 常规新增/修改（GREEN 验证上下文，测试 `[自动化]` 用例）：
          PASS → test-verify 更新状态为 `[新增|修改: 已测试]`，清空 `Issues`，重置 `Retry Count`。继续下一个 spec
          FAIL → test-verify 按失败路由协议分类写入 `Issues`，标记 `[新增|修改: 待修复]`，递增 `Retry Count`。
          code-generate 收到结果后**立即停止**，不继续后续 spec，按 Issues 类型醒示用户下一步命令
        - 轻量（轻量验收上下文）：test-verify 执行轻量验收清单（全量构建 + 类型检查 + `[人工]` 落地核验）。
          PASS → 更新状态为 `[新增|修改: 已测试]`；FAIL → 同上 FAIL 流程
        - 废弃（GREEN 验证上下文）：test-verify 执行验证清单（定向测试 + 全量构建 + grep 引用扫描）。
          PASS → 保持 `[废弃: 已解引用]`；FAIL → `[废弃: 待修复]`，按失败路由协议分类写入 `Issues` 并递增 `Retry Count`，醒示用户

### 待修复规格的处理

对于 `[新增|修改|废弃: 待修复]` 规格，**先读 `Issues` 类型，按 AGENTS.md §失败路由协议 分流**：

- **`[实现缺陷]`** → 本命令修复，流程如下：
  1. 读取 `Issues` 失败详情，区分失败类型：**断言失败** → 修复实现逻辑；**error**（编译/加载/运行异常）→ 优先排查构建配置与环境。**不得修改测试代码**——若证据指向测试代码问题，经用户确认后将 `Issues` 类型改写为 `[测试缺陷]`，醒示用户运行 `/test-generate`，停止
  2. 定位对应的源文件（从 `Affected Files` 获取）
  3. 分析失败原因 → 修复代码（废弃：修复受影响模块引用后重新解引用，必要时从 `_deprecated/` 移回目标代码）
  4. 重新执行步骤 e/f（`[人工]` + `[自动化]` 验证）
  5. 全部 PASS 后清空 `Issues`，重置 `Retry Count`，状态更新为 `[新增|修改: 已测试]`（废弃规格保持 `[废弃: 已解引用]`）
- **`[测试缺陷]`** → 不修改实现，醒示用户「测试代码需要修复，请运行 `/test-generate`」，停止
- **`[规格缺陷]`** → 不修改实现，醒示用户「规格需要重新定义，请运行 `/specify`」，停止

分类可在举证且用户确认后调整：实现方发现失败根源不在实现时，提出分类变更建议，经用户确认后改写 `Issues` 类型并按新类型路由。

### 共识要求（命令特有）

- Agent 自主完成代码生成，但禁止在用户确认前写入文件
- 每个 spec 生成前必须先意图说明实现逻辑，再展示 diff
- 涉及多个文件的修改/废弃操作，主动说明各文件影响
- 用户提出调整时修订后重新确认
- 通用确认规则遵循 AGENTS.md §交互协议

## 实现约束

- 只允许实现 specs.md 中当前状态的规格（新增/修改 `[新增|修改: 测试已生成]` / Issues 为 `[实现缺陷]` 的 `[新增|修改: 待修复]`；轻量 `[新增|修改: 已定义]`；废弃 `[废弃: 待删除]` / `[废弃: 待修复]`）
- 不允许新增未定义规格
- 必须严格遵循 spec 的 `Interface` 字段（公共接口契约）；轻量规格以 `Spec` 目标为准
- 必须使该 spec 的 `[自动化]` 测试全部通过，并引导用户完成 `[人工]` 测试且结果落地
- 必须处理基础边界情况
- 不允许修改无关文件
- **不允许修改测试代码**——疑似测试错误只能改写 Issues 分类并路由 `/test-generate`
- 代码风格必须遵循 `style_guide.md`
- 修改操作必须先读取现有代码文件
- 废弃操作必须确认无其他模块依赖
- 废弃规格必须按 `Depended By` 解引用后移入 `_deprecated/`，禁止直接删除目标代码
- 废弃规格移动后必须请用户人工确认 `_deprecated/` 已从构建/测试配置中排除（不做自动探测）

## 输入来源

本命令的输入从上游文档读取，无需额外 JSON 输入。

### 上游文档

| 文件 | 用途 | 关键内容 |
|------|------|---------|
| `./style_guide.md` | 代码风格规范 | 读取完整文件内容。首次执行时若不存在，调用 `style-resolver` skill 自动生成 |
| `planning/specs.md` | 实现规格 | 筛选 `[新增|修改: 测试已生成]`、轻量`[新增|修改: 已定义]`、`[废弃: 待删除]`、`[新增|修改|废弃: 待修复]` 状态的规格。提取 `Interface`、`Spec`、`Test Double`（如有）、`Test Cases`、`Affected Files`、`轻量`、`Depended By`（废弃规格）。`[新增|修改|废弃: 待修复]` 时额外读取 `Issues`（含分类）、`Retry Count` |
| `planning/plan.md` | 需求背景 + 计划图 | `# Goal`、`# Scope`、`# Constraints` 章节，以及当前工作项的变更类型、描述、设计引用、失败路由（含覆盖声明），作为代码实现的上下文参考 |

### 状态过滤

忽略终态规格（`[新增|修改: 已验证]`、`[废弃: 已删除]`）及未就绪规格（非轻量的 `[新增|修改: 已定义]`、`[废弃: 已解引用]`）。

仅处理 `[新增|修改: 测试已生成]`、轻量 `[新增|修改: 已定义]`、`[废弃: 待删除]`、`Issues` 为 `[实现缺陷]` 的 `[新增|修改|废弃: 待修复]` 规格；`Issues` 为 `[测试缺陷]` / `[规格缺陷]` 的 `[新增|修改|废弃: 待修复]` 规格不属于本命令，按失败路由协议提醒用户。

### 处理顺序

仅处理当前活跃工作项下的规格。按 `planning/specs.md` 中该工作项的规格从上到下顺序依次处理。

**垂直切片模式**：每个 spec 完整走完「读测试 → 解释逻辑 → 实现 → `[人工]` 验证（含落地）→ `/test-verify` 验证」后，再处理下一个 spec。任一 spec 验证 FAIL 时立即停止，不继续后续 spec。

当前活跃工作项 = `planning/plan.md` 中首个「Depends On 全部 DONE」的 TODO/ACTIVE 工作项。若不存在可处理的工作项，提醒用户先运行 `/specify`（有 TODO 未展开时）或 `/plan`（工作项全空时）。

### 上游文档解析提示

- 规格的 `Interface` 为函数签名/API 端点/类型定义，是实现的精确契约；轻量规格可无此字段
- 规格的 `Test Double` 字段（如有）由 specify 定义，test-generate 生成其实现代码。code-generate 据此生成生产实现（二者共享 Interface）
- 规格的 `Test Cases` 为行为验证场景列表，agent 需读取测试代码对照 `[自动化]` 条目；`[人工]` 条目在步骤 e 引导用户执行并回写结果
- `Issues` 字段格式为 `[实现缺陷|测试缺陷|规格缺陷] <详情>`，决定待修复规格的处理分流
- 规格状态标记位于章节标题：`## [新增: 测试已生成] name`、`## [修改: 测试已生成] name`
- `Affected Files` 中的测试文件路径和 Test Double 文件路径由 test-generate 写入，源文件路径由本命令追加。废弃规格无测试文件，`Affected Files` 为引用方文件、目标代码原始路径与移动后 `_deprecated/` 内文件路径

## 输出

命令执行后为 `[新增|修改: 测试已生成]`、轻量 `[新增|修改: 已定义]` 或 `[新增|修改|废弃: 待修复]` 规格生成/修改实现代码，通过全部验证（`[人工]` 落地 + `/test-verify`）后，由 test-verify 更新状态为 `[新增|修改: 已测试]`。

## 下一步

- 所有 spec 实现完成（新增/修改状态 `[新增|修改: 已测试]`，废弃状态 `[废弃: 已解引用]`）→ 提醒用户运行 `/code-review`
- 存在 `[新增|修改|废弃: 待修复]` → 按 Issues 分类提醒下一步：`[实现缺陷]` 重新运行 `/code-generate`；`[测试缺陷]` 运行 `/test-generate`；`[规格缺陷]` 运行 `/specify`

## 约束

- 不允许跨规格实现
- 不允许跳过依赖工作项（Depends On 未 DONE 的工作项不得实现）
- 不允许生成伪代码
- 常规规格不允许在未读测试代码的情况下生成实现
- 任何 spec FAIL 时立即停止，不自动重试，不处理后续 spec
- 修改操作必须先读取现有代码文件
- 废弃操作必须确认无其他模块依赖
- 若 spec 声明了 Test Double → 必须同时生成生产实现，不可仅依赖 Test Double
- Interface 是唯一真相源，Test Double 和生产实现共享此契约
- `[人工]` 测试 ALL PASS 且结果已回写 specs.md 后才可进入 `/test-verify`
- `[人工]` 测试 FAIL 时不可跳过，必须按失败路由协议分类标记 `[新增|修改|废弃: 待修复]` 并停止
- 永不修改测试代码；测试问题一律分类路由 `/test-generate`
- `[规格缺陷]` 一律路由 `/specify`，不得自行修改规格
