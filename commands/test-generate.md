---
name: test-generate
description: TDD 红阶段——根据规格的 Interface 和 Test Cases 生成测试代码，确认测试在代码实现前处于 FAIL 状态；并受理 `[测试缺陷]` 路由的测试修复
---

## 功能说明

该命令是 TDD 流程的第二步（RED 阶段），在 code-generate **之前**执行。
根据规格的 `Interface`、`Test Double`（如有）和 `Test Cases` 字段，
对 `[自动化]` 条目生成测试代码和 Test Double 实现（如有），运行测试确认 FAIL（RED）；
对 `[人工]` 条目汇编为结构化 checklist，不生成代码。

根据规格的操作类型，采用不同的测试策略：

- **新增**：完整功能测试（通过公共接口验证行为）。若 spec 声明了 Test Double，先生成 Test Double 实现，测试注入 Test Double
- **修改**：回归测试 + 新行为验证。若 spec 声明了 Test Double，先生成 Test Double 实现，测试注入 Test Double
- **废弃**：跳过测试生成——验证手段已由 specify 以清单形式写入 `Test Cases`（受影响模块定向测试、全量构建、grep 引用扫描），由 `/code-generate` 解引用后经 `/test-verify` 执行
- **轻量**：跳过测试生成——轻量规格无 `[自动化]` 用例，由 `/code-generate` 直接实现，经 `/test-verify` 轻量验收

本命令同时是测试代码的唯一责任方：受理 AGENTS.md §失败路由协议 路由而来的 `[测试缺陷]` 规格，修复其测试代码。其他任何命令不得修改测试代码。

## 行为规则

执行流程：

0. 检查项目根目录 `AGENTS.md` 已包含工作流共识（含「失败路由协议」节）；若缺失，醒示用户先运行 `/setup` 初始化并终止。读取 `./style_guide.md`。如不存在，调用 `style-resolver` skill 从项目配置自动生成代码风格规范，经用户确认后写入，再继续后续流程
1. 读取 `planning/specs.md` 与 `planning/plan.md`
2. 确定处理对象：
   - **RED 主线**：选取非轻量的 `[新增|修改: 已定义]` 规格（`[废弃: 待删除]` 与轻量 `[新增|修改: 已定义]` 跳过，提醒直接 `/code-generate`）
   - **测试缺陷受理**：选取 `Issues` 以 `[测试缺陷]` 开头的 `[新增|修改: 待修复]` 规格（见「`[测试缺陷]` 规格的受理」）
3. 检测测试框架：检查项目依赖配置文件（如 `package.json` / `go.mod` / `Cargo.toml` / `requirements.txt` 等）中声明的测试依赖，结合已有测试文件的导入语句确定测试框架。无法确定则询问用户
4. 逐 spec 处理（垂直切片），每个 spec 执行以下子步骤：

   a. **意图说明测试思路**：向用户说明该 spec 的测试策略——
      验证什么行为、Test Double 设计（如有）、`[自动化]` 与 `[人工]` 的划分理由

   b. **解析 Test Cases**：分离 `[自动化]` 与 `[人工]` 条目

   c. **生成 Test Double 代码**（若 spec 声明了 Test Double）：
      基于 spec 的 `Test Double` 字段（类型、数据结构、行为约定、暴露接口），
      生成 Test Double 实现代码，写入测试辅助目录。将 Test Double 文件路径追加到 `Affected Files`

   d. **生成测试代码预览**：基于该 spec 的 `Interface` 和 `Test Cases` 中的 `[自动化]` 条目，
      生成测试代码 diff/文件预览。若存在 Test Double，测试中注入 Test Double

   e. **等待用户确认**：用户确认测试代码无误后，写入测试文件。若用户提出修改意见 → 回到 d 修订

   f. **运行测试确认 RED**：调用 `/test-verify`（RED 确认上下文），执行 `[自动化]` 测试
      - **断言失败**（预期 FAIL，RED 确认成功）→ 标记该 spec 状态为 `[新增: 测试已生成]` 或 `[修改: 测试已生成]`，继续下一个 spec
      - **error**（编译/加载/运行异常）→ 醒示用户「测试代码无法编译或运行——可能原因：缺少 stub 占位、引用不存在的符号或环境问题。请检查后重试」。不更新状态
      - **意外 PASS**（测试未按预期失败）→ 醒示用户「测试意外通过——可能原因：代码已存在实现，或测试断言有误。请确认后重试」。不更新状态

      （若 error 源于「实现符号不存在」：agent 提议生成最小 stub 占位——仅满足编译、不实现行为，经用户确认后写入目标源文件位置并明确标注占位，再重新运行 RED 确认。stub 由后续 code-generate 替换为真实实现，不得提前标记 `[新增|修改: 已实现]`）

   g. **汇编 [人工] checklist**：将 `[人工]` 条目汇编为结构化清单输出，标注「以下测试需在 code-generate 完成实现后执行，执行结果由 code-generate 回写 specs.md」。不生成任何代码

   h. **写入 Affected Files**：测试文件路径 + Test Double 文件路径（如有）+ stub 占位源文件路径（如有）追加写入

5. 所有 spec 处理完毕后，汇总输出执行结果

### `[测试缺陷]` 规格的受理

当规格处于 `[新增|修改: 待修复]` 且 `Issues` 以 `[测试缺陷]` 开头（由 test-verify 或 code-review 按 AGENTS.md §失败路由协议 分类路由）时，本命令是唯一有权修复测试代码的入口：

1. 读取 `Issues` 失败详情与 spec 的 `Interface` / `Test Cases`
2. 基于规格重新推导测试代码——只信规格，不参考现有实现；修正断言、用例结构或 Test Double 行为映射中的错误
3. 展示修复 diff 预览，用户确认后写入；测试文件路径追加 `Affected Files`（去重）
4. 清空 `Issues`，重置 `Retry Count` 为 0，状态回写 `[新增: 测试已生成]` 或 `[修改: 测试已生成]`
5. **不做 RED 重新确认**——实现代码可能已存在，RED 前提不适用；测试正确性以规格为准，行为验证交给 GREEN。提醒用户「测试已修复，请重新运行 `/code-generate` 继续 GREEN 验证」

若修复中发现测试期望与规格本身矛盾，问题不在测试而在规格：不修改测试，将 `Issues` 改写为 `[规格缺陷] <说明>`，醒示用户运行 `/specify`。

### 废弃规格与轻量规格的处理

`[废弃: 待删除]` 与轻量规格不进入本命令——不生成任何测试代码，也不做 RED 确认：

- 废弃规格的验证手段已在 specify 阶段以清单形式写入 `Test Cases`（受影响模块定向测试、全量构建、grep 引用扫描），由 `/code-generate` 完成解引用与移动后，经 `/test-verify` 执行
- 轻量规格无 `[自动化]` 用例（其 `Test Cases` 仅含 `[人工]` 条目或构建/类型检查清单），由 `/code-generate` 直接实现，经 `/test-verify` 轻量验收

### 测试质量规范

Agent 生成测试时必须遵循以下纪律。这些规则确保测试在代码重构时不会脆断。

#### 核心原则：测试行为，不测试实现

**好测试**（通过公共接口验证行为）：

- 测试 WHAT（用户可结账），不测试 HOW（调用了 process 方法）
- 使用公共 API 进行验证
- 能承受内部重构（改函数名、调整内部结构后测试不脆断）
- 每个测试验证一个明确的行为

**坏测试**（耦合到实现细节）：

- Mock 内部协作者
- 测试私有方法
- 断言调用顺序/次数
- 绕过接口直接验证内部状态（如直接查数据库而非通过 API）
- 重构时测试脆断但行为未变

#### Mock 纪律：仅在系统边界 Mock

| 应该 Mock | 不应该 Mock |
| ----------- | ------------ |
| 外部 API（支付、邮件、第三方服务） | 自己的类/模块 |
| 数据库（优先使用测试专用 DB） | 内部协作者 |
| 时间/随机数 | 项目中可控制的对象 |
| 文件系统（必要时） | 工具函数/辅助模块 |

#### 接口设计原则（引导 Agent）

- 优先使用依赖注入，使外部依赖可被替换
- 为每个外部操作创建独立的 SDK 风格函数，避免使用泛化的 fetcher
- 系统边界的接口设计应易于 Mock

## 输入来源

本命令的输入从上游文档读取，无需额外 JSON 输入。

### 上游文档

| 文件 | 用途 | 关键内容 |
| ------ | ------ | --------- |
| `./style_guide.md` | 代码风格规范 | 读取完整文件内容。首次执行时若不存在，调用 `style-resolver` skill 自动生成 |
| `planning/specs.md` | 实现规格 | 筛选非轻量的 `[新增 | 修改: 已定义]` 规格与 `[测试缺陷]` 标记的 `[新增 | 修改: 待修复]` 规格，提取 `Interface`、`Test Double`（如有）、`Test Cases`、`Issues`（操作类型取自规格标题）。废弃与轻量规格跳过 |
| `planning/plan.md` | 计划图 | 定位当前活跃工作项（首个「Depends On 全部 DONE」的 TODO/ACTIVE） |

### 状态过滤

忽略终态规格（`[新增|修改: 已验证]`）及已进入后续阶段的规格（`[新增|修改: 测试已生成]`、`[新增|修改: 已实现]`、`[新增|修改: 已测试]`）。

仅处理：非轻量的 `[新增|修改: 已定义]`（RED 主线）；`Issues` 以 `[测试缺陷]` 开头的 `[新增|修改: 待修复]`（缺陷受理，唯一例外）。废弃规格（`[废弃: 待删除]`）与轻量 `[新增|修改: 已定义]` 规格不进入本命令。

### 处理顺序

仅处理当前活跃工作项下的规格。按 `planning/specs.md` 中该工作项的规格从上到下顺序依次处理。当前活跃工作项 = `planning/plan.md` 中首个「Depends On 全部 DONE」的 TODO/ACTIVE 工作项。若不存在可处理的工作项，提醒用户先运行 `/specify`（有 TODO 未展开时）或 `/plan`（工作项全空时）。

### 上游文档解析提示

- `Interface` 字段为精确的函数签名/API 端点/类型定义，是测试代码的直接契约依据；轻量规格可无此字段
- `Test Double` 字段（如有）包含测试替身的类型、数据结构、行为约定和暴露接口，agent 据此生成 Test Double 实现
- `Test Cases` 字段为行为验证场景列表，标记 `[自动化]` 或 `[人工]`（`[人工]` 条目可能带 code-generate 回写的 `✓ PASS` / `✗ FAIL` 标记）。agent 仅为 `[自动化]` 条目生成测试代码；`[人工]` 条目汇编为 checklist
- `轻量` 字段标记该规格是否走轻量流程
- `Issues` 字段格式为 `[实现缺陷|测试缺陷|规格缺陷] <详情>`，本命令仅受理 `[测试缺陷]` 开头的规格
- 规格状态标记位于章节标题：`## [新增: 已定义] name`、`## [修改: 已定义] name`、`## [废弃: 待删除] name`

## 输出

命令执行后为 `[新增|修改: 已定义]` 状态规格生成测试代码，RED 确认后更新状态为 `[新增|修改: 测试已生成]`；为 `[测试缺陷]` 规格修复测试代码，状态回写 `[新增|修改: 测试已生成]`。

### Markdown 预览

```md
## 测试分析

### [新增: 已定义] spec_name
- 测试策略: <整体策略说明>
- Test Double: <类型与用途（如有）>
- `[自动化]` 覆盖场景: <列出>
- `[人工]` 覆盖场景: <列出>

## [自动化] 测试代码

+ Test Double 实现代码（如有）
+ 新增测试代码

## RED 确认

| 规格 | 测试文件 | 预期 | 实际 | 失败类型 | RED 确认 |
|------|---------|------|------|---------|---------|
| spec_a | src/__tests__/a.test.ts | FAIL | FAIL | 断言失败 | ✓ RED |
| spec_b | src/__tests__/b.test.ts | FAIL | PASS | - | ⚠ 意外通过 |
| spec_c | src/__tests__/c.test.ts | FAIL | FAIL | error（编译失败） | ✗ 未确认 |

## [人工] 测试 Checklist（待 code-generate 完成后执行并回写 specs.md）

| 规格 | 操作 | 预期 | 通过标准 |
|------|------|------|---------|
| spec_c | 打开登录页... | 红色提示文字... | 颜色/位置/内容一致 |

## [测试缺陷] 修复（如有）

| 规格 | Issues 摘要 | 修复内容 | 新状态 |
|------|------------|---------|--------|
| spec_d | [测试缺陷] 断言与规格矛盾... | 修正断言依据规格 4.2... | [修改: 测试已生成] |
```

## 下一步

- 所有规格 RED 确认（或为轻量/废弃规格，无测试可做）→ 提醒用户运行 `/code-generate` 实现代码（TDD: GREEN 阶段）
- 存在意外 PASS 或 error → 请用户排查后重新运行本命令
- 受理了 `[测试缺陷]` 规格 → 提醒用户运行 `/code-generate`

## 约束

- 必须基于 spec 的 `Interface` 字段编写测试（通过公共接口验证）
- 必须覆盖 spec 的 `Test Cases` 中所有 `[自动化]` 场景
- 禁止为 `[人工]` 条目生成测试代码
- 若 spec 声明了 Test Double，必须先生成 Test Double 实现再生成测试代码
- Test Double 的行为约定必须原样映射为代码
- 不允许 Mock 内部模块/协作者
- 不允许测试私有方法或实现细节
- 测试代码风格必须遵循 `style_guide.md`
- 修改类型规格必须包含回归测试
- 废弃与轻量规格跳过测试生成，不生成任何测试代码
- RED 确认失败时不可继续，必须醒示用户排查
- error 不允许确认 RED——必须先解决编译/加载/运行问题（可生成 stub 占位）后重试
- 不允许跳过 RED 确认直接标记 `[新增|修改: 测试已生成]`
- 仅受理 `[测试缺陷]` 类型的 `[新增|修改: 待修复]` 规格；`[实现缺陷]` / `[规格缺陷]` 不属于本命令，提醒用户按 AGENTS.md §失败路由协议 路由（`[规格缺陷]` → `/specify`）
- `[测试缺陷]` 修复只信规格，不参考现有实现；修复后不做 RED 重新确认
- 修复中发现测试期望与规格矛盾时，改写 Issues 为 `[规格缺陷]` 并路由 `/specify`，不得擅自调整规格
