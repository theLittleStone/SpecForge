---
name: test-generate
description: TDD 红阶段——根据规格的 Interface 和 Test Cases 生成测试代码，确认测试在代码实现前处于 FAIL 状态
---

## 功能说明

该命令是 TDD 流程的第二步（RED 阶段），在 code-generate **之前**执行。
根据规格的 `Interface`、`Test Double`（如有）和 `Test Cases` 字段，
对 `[自动化]` 条目生成测试代码和 Test Double 实现（如有），运行测试确认 FAIL（RED）；
对 `[人工]` 条目汇编为结构化 checklist，不生成代码。

根据规格的操作类型，采用不同的测试策略：
- **新增**：完整功能测试（通过公共接口验证行为）。若 spec 声明了 Test Double，先生成 Test Double 实现，测试注入 Test Double
- **修改**：回归测试 + 新行为验证。若 spec 声明了 Test Double，先生成 Test Double 实现，测试注入 Test Double
- **废弃**：副作用检查（生成验证无悬空引用、无残留调用的测试）

## 行为规则

执行流程：

0. 读取 `./style_guide.md`。如不存在，调用 `style-resolver` skill 自动生成
1. 读取 `planning/specifications.md`
2. 选择状态为 `[新增: 已定义]`、`[修改: 已定义]` 或 `[废弃: 待删除]` 的规格
3. 检测测试框架：检查项目依赖配置文件（如 `package.json` / `go.mod` / `Cargo.toml` / `requirements.txt` 等）中声明的测试依赖，结合已有测试文件的导入语句确定测试框架。无法确定则询问用户
4. 逐 spec 处理（垂直切片），每个 spec 执行以下子步骤：

   a. **意图说明测试思路**：向用户说明该 spec 的测试策略——
      验证什么行为、Test Double 设计（如有）、`[自动化]` 与 `[人工]` 的划分理由。
      用户确认理解后再进入下一步

   b. **解析 Test Cases**：分离 `[自动化]` 与 `[人工]` 条目

   c. **生成 Test Double 代码**（若 spec 声明了 Test Double）：
      基于 spec 的 `Test Double` 字段（类型、数据结构、行为约定、暴露接口），
      生成 Test Double 实现代码，写入测试辅助目录。将 Test Double 文件路径追加到 `Affected Files`

   d. **生成测试代码预览**：基于该 spec 的 `Interface` 和 `Test Cases` 中的 `[自动化]` 条目，
      生成测试代码 diff/文件预览。若存在 Test Double，测试中注入 Test Double

   e. **等待用户确认**：用户确认测试代码无误后，写入测试文件。若用户提出修改意见 → 回到 d 修订

   f. **运行测试确认 RED**：调用 `/test-verify`（RED 确认上下文），执行 `[自动化]` 测试
      - **预期 FAIL**（RED 确认成功）→ 标记该 spec 状态为 `[新增: 测试已生成]` 或 `[修改: 测试已生成]` 或 `[废弃: 测试已生成]`，继续下一个 spec
      - **意外 PASS**（测试未按预期失败）→ 醒示用户「测试意外通过——可能原因：代码已存在实现，或测试断言有误。请确认后重试」。不更新状态

   g. **汇编 [人工] checklist**：将 `[人工]` 条目汇编为结构化清单输出，标注「以下测试需在 code-generate 完成实现后执行」。不生成任何代码

   h. **写入 Affected Files**：测试文件路径 + Test Double 文件路径（如有）追加写入

5. 所有 spec 处理完毕后，汇总输出执行结果

### 废弃规格的处理差异

对于 `[废弃: 待删除]` 规格：
- 生成的测试应验证「待删除代码被移除后无副作用」——即测试断言：删除后相关模块行为不受影响
- RED 确认阶段：测试预期行为与新增/修改不同——此时代码尚未删除，测试验证代码仍存在时的影响范围，后续 code-generate 删除代码后由 test-verify 确认无副作用

### 测试质量规范

Agent 生成测试时必须遵循以下纪律。这些规则确保测试在代码重构时不会脆断。

#### 核心原则：测试行为，不测试实现

**好测试**（通过公共接口验证行为）：

- 测试 WHAT（用户可结账），不测试 HOW（调用了 process 方法）
- 使用公共 API 进行验证
- 能承受内部重构（改函数名、调整内部结构后测试不脆断）
- 每个测试验证一个明确的行为

**坏测试**（耦合到实现细节）：

- Mock 内部协作者
- 测试私有方法
- 断言调用顺序/次数
- 绕过接口直接验证内部状态（如直接查数据库而非通过 API）
- 重构时测试脆断但行为未变

#### Mock 纪律：仅在系统边界 Mock

| 应该 Mock | 不应该 Mock |
|-----------|------------|
| 外部 API（支付、邮件、第三方服务） | 自己的类/模块 |
| 数据库（优先使用测试专用 DB） | 内部协作者 |
| 时间/随机数 | 项目中可控制的对象 |
| 文件系统（必要时） | 工具函数/辅助模块 |

#### 接口设计原则（引导 Agent）

- 优先使用依赖注入，使外部依赖可被替换
- 为每个外部操作创建独立的 SDK 风格函数，避免使用泛化的 fetcher
- 系统边界的接口设计应易于 Mock

## 输入来源

本命令的输入从上游文档读取，无需额外 JSON 输入。

### 上游文档

| 文件 | 用途 | 关键内容 |
|------|------|---------|
| `./style_guide.md` | 代码风格规范 | 读取完整文件内容。首次执行时若不存在，调用 `style-resolver` skill 自动生成 |
| `planning/specifications.md` | 实现规格 | 筛选 `[新增: 已定义]`、`[修改: 已定义]`、`[废弃: 待删除]` 状态的规格，提取 `Interface`、`Test Double`（如有）、`Test Cases`、`Change Type` |
| `planning/tasks.md` | 任务列表 | 定位当前活跃 task（首个 `[DEFINED]`） |

### 状态过滤

忽略终态规格（`[新增: 已验证]`、`[修改: 已验证]`、`[废弃: 已删除]`）及已进入后续阶段的规格（`[新增: 测试已生成]`、`[修改: 测试已生成]`、`[新增: 已实现]`、`[修改: 已实现]`、`[新增: 已测试]`、`[修改: 已测试]`、`[新增: 待修复]`、`[修改: 待修复]`）。

仅处理 `[新增: 已定义]`、`[修改: 已定义]`、`[废弃: 待删除]` 状态的规格。

### 处理顺序

仅处理当前活跃 task 下的规格。按 `planning/specifications.md` 中该 task 的规格从上到下顺序依次处理。当前活跃 task = `planning/tasks.md` 中首个标题标记为 `[DEFINED]` 的任务。若不存在 DEFINED 任务，提醒用户先运行 `/specification-define`。

### 上游文档解析提示

- `Interface` 字段为精确的函数签名/API 端点/类型定义，是测试代码的直接契约依据
- `Test Double` 字段（如有）包含测试替身的类型、数据结构、行为约定和暴露接口，agent 据此生成 Test Double 实现
- `Test Cases` 字段为行为验证场景列表，标记 `[自动化]` 或 `[人工]`。agent 仅为 `[自动化]` 条目生成测试代码；`[人工]` 条目汇编为 checklist
- 规格状态标记位于章节标题：`## [新增: 已定义] name`、`## [修改: 已定义] name`、`## [废弃: 待删除] name`

## 输出

命令执行后为 `[已定义]` 状态规格生成测试代码，RED 确认后更新状态为 `[测试已生成]`。

```md
## 测试分析

- 测试策略: <整体策略说明>
- Test Double: <类型与用途（如有）>
- `[自动化]` 覆盖场景: <列出>
- `[人工]` 覆盖场景: <列出>

## [自动化] 测试代码

+ Test Double 实现代码（如有）
+ 新增测试代码

## RED 确认

| 规格 | 测试文件 | 预期 | 实际 | RED 确认 |
|------|---------|------|------|---------|
| spec_a | src/__tests__/a.test.ts | FAIL | FAIL | ✓ RED |
| spec_b | src/__tests__/b.test.ts | FAIL | PASS | ⚠ 意外通过 |

## [人工] 测试 Checklist（待 code-generate 完成后执行）

| 规格 | 操作 | 预期 | 通过标准 |
|------|------|------|---------|
| spec_c | 打开登录页... | 红色提示文字... | 颜色/位置/内容一致 |
```

## 下一步

- 所有规格 RED 确认 → 提醒用户运行 `/code-generate` 实现代码（TDD: GREEN 阶段）
- 存在意外 PASS → 请用户排查后重新运行本命令

## 约束

- 必须基于 spec 的 `Interface` 字段编写测试（通过公共接口验证）
- 必须覆盖 spec 的 `Test Cases` 中所有 `[自动化]` 场景
- 禁止为 `[人工]` 条目生成测试代码
- 若 spec 声明了 Test Double，必须先生成 Test Double 实现再生成测试代码
- Test Double 的行为约定必须原样映射为代码
- 不允许 Mock 内部模块/协作者
- 不允许测试私有方法或实现细节
- 测试代码风格必须遵循 `style_guide.md`
- 修改类型规格必须包含回归测试
- 废弃类型规格必须生成副作用验证测试
- RED 确认失败时不可继续，必须醒示用户排查
- 不允许跳过 RED 确认直接标记 `[测试已生成]`
