## 功能说明

该命令是 TDD 流程的第四步（REFACTOR 阶段），在所有测试通过后执行。

职责包括三个层次：
1. **代码审查**：正确性、规格一致性、安全与性能检查
2. **重构**：消除重复、深化模块、应用 SOLID 原则——每次重构后运行回归测试
3. **测试代码审查**：验证测试质量（是否测试行为而非实现、是否存在脆弱测试）

该阶段是最终确认阶段。审查通过后触递归上溯，将 task 标记为 `[IMPLEMENTED]`。

## 行为规则

执行流程：

### Phase 1 — 审查阶段（只读，不修改代码）

1. 读取 `planning/specifications.md`
2. 读取 `./style_guide.md`
3. 检查状态为 `[新增: 已测试]`、`[修改: 已测试]`、`[废弃: 已解引用]` 的规格（即待审查状态）
4. 逐 spec 审查（垂直切片），每个 spec 执行以下子步骤：

   a. **意图说明审查发现**：向用户说明——该 spec 代码中发现了什么问题、严重程度。用户确认理解后再进入下一步

   b. **代码审查**：根据操作类型执行差异化审查（详见「审查内容 → 代码审查」检查项）：
      - **新增**：正确性、规格一致性、风格检查、注释补全
      - **修改**：diff 审查（仅审查变更部分）、兼容性检查、回归风险分析
      - **废弃**：确认引用方已全部解引用、代码已移入 `_deprecated/`、检查悬空引用与残留引用

   c. **Test Double 审查**（若 spec 声明了 Test Double）：
      - Test Double 实现是否忠实地遵循 spec 的 `Test Double` 字段中的行为约定
      - 暴露接口是否正确暴露内部状态（供测试断言使用）
      - 生产实现与 Test Double 是否共享同一 `Interface`

   d. **测试代码质量审查**（与代码审查并行，详见「审查内容 → 测试代码质量审查」检查项）：
      - 测试是否通过公共接口验证行为（WHAT）而非实现（HOW）
      - Mock 是否仅限系统边界
      - 测试是否会在内部重构时脆断
      - 是否覆盖 spec 的 `Test Cases` 全部 `[自动化]` 场景
      - 是否存在冗余测试

   e. **[人工] 测试完成性确认**：
      - 若 spec 含 `[人工]` 条目 → 检查 code-generate 输出中 `[人工]` 测试结果是否全部 PASS
      - 若存在未完成或 FAIL 的 `[人工]` 条目 → 醒示用户，spec 不标记终态，保持 `[已测试]`

5. 所有 spec 审查完毕后，汇总输出审查发现清单（按严重程度排列），等待用户确认。用户确认后进入 Phase 2。

### Phase 2 — 重构阶段（读写，每次重构后回归测试）

6. 基于审查发现清单，识别重构机会。按以下检查清单逐项处理：
   - **去重** → 提取重复代码为函数/类
   - **深化模块** → 将复杂性隐藏在简洁接口后
   - **SOLID 应用** → 在自然时机应用单一职责、开闭原则等
   - **长函数拆分** → 将过长函数拆为私有辅助函数（保持测试在公共接口上）
   - **特性依恋修复** → 将逻辑移动至数据所在位置
   - **基本类型偏执修复** → 引入值对象（Value Object）
   - **死代码清理** → 移除新代码中暴露的未使用/不可达代码

   逐项重构，每项执行：

   a. **意图说明重构思路**：向用户说明——为什么重构、预期收益、风险提示。用户确认后再展示 diff

   b. **执行重构**：修改代码，写入文件

   c. **回归测试**：运行 `/test-verify`：
      - **PASS** → 该重构项完成，继续下一项
      - **FAIL** → 立即回退本次重构改动，醒示用户「重构引入了意外行为变更，已回退。原因：<details>」。该项标记为跳过，继续下一项

   **关键纪律**：
   - **绝不在 RED 时重构** — 所有测试必须 GREEN 才开始重构
   - **禁止批量重构** — 每次只改一个重构项，回归测试通过后再进行下一项

7. 风格/注释修正等小改动可在 Phase 1 审查确认后直接纳入 Phase 2 执行
8. 所有修改完成后，将改动的文件路径追加写入 `planning/specifications.md` 中对应规格的 `Affected Files` 字段（与已有路径去重）
9. 递归上溯传播状态（详见「递归上溯」章节）

### 共识要求

- Agent 自主完成审查分析与重构方案设计，但禁止在用户确认前修改文件
- Phase 1 中每个 spec 审查前必须先意图说明发现的问题，用户确认后再展开审查细节
- Phase 2 中每项重构前必须先意图说明重构思路、预期收益与风险，用户确认后展示 diff
- 风格/注释修正等小改动纳入提案展示，确认后写入
- 严重设计问题说明问题本质与建议方向，由用户决策
- 重构提案需说明：为什么重构、预期收益、风险提示
- 每次重构后必须运行回归测试

## 审查内容

### 代码审查

- 是否严格遵循 Spec 描述与 `Interface` 契约
- 是否存在未覆盖情况
- 是否符合代码风格规范
- 是否包含完整 docstring / 注释
- 对于修改类型：diff 中是否有意外副作用
- 对于废弃类型：是否有残留引用、`_deprecated/` 是否已从构建/测试配置中排除、与 `# Dependency Index` 是否一致
- 是否存在未使用/不可达的死代码
- 是否存在安全基础问题（硬编码密钥/Token、用户输入未校验直接使用、SQL/HTML 拼接等）
- 是否存在明显性能隐患（如循环内同步 I/O、不必要的大对象深拷贝、可降 O(n) 的嵌套循环等）
- 是否存在魔法数字（逻辑/配置中使用未命名常量的字面量，排除 -1/0/1/2 等常见边界值）
- 是否存在嵌套深度 > 3 的函数
- 单函数行数是否超出 style_guide.md 定义的上限（若 style_guide 未定义此条目则跳过）

### 测试代码质量审查

- **行为 vs 实现**：测试是否通过公共接口验证行为（WHAT），而非耦合到实现细节（HOW）
- **Mock 纪律**：是否在系统边界以外 Mock（内部模块/协作者不应被 Mock）
- **脆弱性**：测试是否会在内部重构时脆断——可承受改函数名、调整内部结构？
- **覆盖完整性**：是否覆盖了 spec 的 `Test Cases` 中列出的所有 `[自动化]` 场景
- **重复测试**：是否存在验证同一行为的冗余测试
- **Test Double 实现质量**：是否忠实于 spec 的行为约定、暴露接口是否合理
- **[人工] Checklist 完整性**：是否每项含操作/预期/通过标准三要素

## 输入来源

本命令的输入从上游文档读取，无需额外 JSON 输入。

### 上游文档

| 文件 | 用途 | 关键内容 |
|------|------|---------|
| `planning/specifications.md` | 实现规格 | 筛选 `[新增: 已测试]`、`[修改: 已测试]`、`[废弃: 已解引用]` 状态的规格，提取 `Change Type`、`Task`、`Spec` |
| `planning/tasks.md` | 任务列表 | `# Task List` 中各 task 的 `Specs` 字段（规格→task 映射），用于递归上溯判断 |
| `./style_guide.md` | 代码风格规范 | 读取完整文件内容，作为审查的编码规范依据 |

### 状态过滤

忽略终态规格（`[新增: 已验证]`、`[修改: 已验证]`、`[废弃: 已删除]`）。仅处理 `[新增: 已测试]`、`[修改: 已测试]`、`[废弃: 已解引用]` 状态的规格。

### 处理顺序

仅处理当前活跃 task 下的规格。按 `planning/specifications.md` 中该 task 的规格从上到下顺序依次审查。当前活跃 task = `planning/tasks.md` 中首个标题标记为 `[DEFINED]` 的任务。若不存在 DEFINED 任务，提醒用户先运行 `/specification-define`。

### 上游文档解析提示

- 待审查规格通过章节标题状态标记识别：`## [新增: 已测试] name`、`## [修改: 已测试] name`、`## [废弃: 已解引用] name`

## 递归上溯

审查通过后，code-review 执行递归上溯，逐层向上传播完成信号：

1. **从规格反查所属 task**：通过 `planning/specifications.md` 中该规格的 `Task` 字段定位所属 task
2. **检查该 task 下所有规格是否全部终态**：遍历 `planning/tasks.md` 中该 task 的 `Specs` 字段关联的所有规格
   - 新增类规格 → 必须全部 `[新增: 已验证]`（`[新增: 已测试]` 不为终态）
   - 修改类规格 → 必须全部 `[修改: 已验证]`（`[修改: 已测试]` 不为终态）
   - 废弃类规格 → 必须全部 `[废弃: 已解引用]`（物理删除由 progress-report 收尾）
3. **若全部终态**：将该 task 标题标记更新为 `[IMPLEMENTED]`
4. **跨 task 扫描**：扫描 `planning/tasks.md` 中所有 task 的状态
   - 全部 IMPLEMENTED → 告知用户「所有 task 已完成，请运行 `progress-report` 收尾」
   - 仍有 TODO/DEFINED → 告知用户「当前 task 已完成，请继续执行下一个 task（运行 `specification-define`）」

## 输出

命令执行后对待验证状态规格的代码进行审查，根据结果更新规格状态，并向上传播完成信号到 `planning/tasks.md`。

规格状态：

- 新增/修改通过 → `[新增: 已验证]` 或 `[修改: 已验证]`（终态）
- 新增/修改发现问题 → 自动修正可修复项（风格、注释、文档等）；若存在严重设计问题无法自动修复，降级为 `[新增: 待修复]` 或 `[修改: 待修复]` 并在 Issues 字段标注，告知用户人工决策
- 废弃 → 检查残留引用、`_deprecated/` 构建排除与索引一致性。通过则保持 `[废弃: 已解引用]`；发现问题则降级为 `[废弃: 待修复]` 并在 Issues 字段标注，告知用户人工决策

## 状态说明

- `[新增: 已测试]` → `[新增: 已验证]`（新增通过审查，且所有 `[人工]` checklist 已确认 PASS）
- `[修改: 已测试]` → `[修改: 已验证]`（修改通过审查，且所有 `[人工]` checklist 已确认 PASS）
- 若存在未确认的 `[人工]` 条目 → 醒示用户完成人工验证，保持 `[已测试]`，不标记终态
- `[废弃: 已解引用]` → 检查残留引用与索引一致性，无问题则保持；发现问题降级为 `[废弃: 待修复]`

## 约束

- 必须基于 style_guide.md
- 不允许忽略规格不一致问题
- 不允许大规模重写代码
- 若存在严重问题，必须返回 fail
- 修改类型必须审查 diff 范围外的潜在影响
- **绝不在 RED 时重构**——所有测试必须 GREEN 才能开始重构
- 每次重构后必须运行回归测试，FAIL 时必须回退重构改动
- 必须审查测试代码质量（行为验证 vs 实现细节验证），发现问题需标注
- 若 spec 声明了 Test Double，必须审查其实现质量（行为约定忠实度、暴露接口合理性）
- 含 `[人工]` 条目的 spec 必须确认全部 checklist PASS 后方可标记终态
