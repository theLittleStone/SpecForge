## 功能说明

该命令是 TDD 流程的第三步（GREEN 阶段），在 test-generate（RED 确认）**之后**执行。

核心原则：**先读测试，再写代码**。agent 必须阅读每个 spec 的测试代码，理解测试断言与行为期望，然后生成实现代码使 `[自动化]` 测试通过，并引导用户完成 `[人工]` 测试。

若 spec 声明了 Test Double，agent 需理解生产实现与 Test Double 共享同一 Interface，通过依赖注入切换。

支持三种操作类型：
- **新增**：根据测试代码，创建新代码文件或添加新代码。若存在 Test Double，同时生成生产实现
- **修改**：根据测试代码的回归保护，修改现有代码
- **废弃**：按 `Depended By` 解引用后移入 `_deprecated/`（不直接删除），验证通过后由 progress-report 收尾统一物理删除

## 行为规则

执行流程：

0. 读取 `./style_guide.md`。如不存在，调用 `style-resolver` skill，从项目配置自动生成代码风格规范，经用户确认后写入，再继续后续流程
1. 读取 `planning/specifications.md`
2. 读取 `planning/requirement.md`，获取 `# Goal`、`# Scope` 作为背景上下文
3. 选择状态为 `[新增: 测试已生成]`、`[修改: 测试已生成]`、`[废弃: 待删除]` 或 `[新增: 待修复]`、`[修改: 待修复]`、`[废弃: 待修复]` 的规格
4. 逐 spec 处理（垂直切片——每个 spec 完成实现和全部验证后，再处理下一个 spec）：

   a. **读取测试代码**：从该 spec 的 `Affected Files` 字段获取测试文件路径和 Test Double 文件路径（如有），
       读取测试代码，理解测试框架、断言逻辑和期望行为。同时读取 spec 的 `Interface` 字段确认公共接口契约。
       若 spec 有 Test Double，理解 Test Double 的行为约定，确认生产实现与 Test Double 共享同一 Interface。
       对于 `[待修复]` 状态，额外读取 `Issues` 字段了解上次失败原因（含 `[人工]` 或 `[自动化]` 失败详情）。
       废弃规格无测试代码，改为读取 `Spec` 与 `Depended By` 定位待删目标及其引用方

   b. **意图说明实现逻辑**：向用户说明——当前 spec 要解决什么问题、实现思路与设计决策、
      涉及哪些源文件、与 Test Double 的关系（如有）。用户确认理解后再进入下一步

   c. **生成实现代码**：根据操作类型分叉：
      - **新增**：根据测试断言 + `Interface` 契约，生成新代码。
        若 spec 有 Test Double，同时生成生产实现（二者共享 Interface，通过依赖注入切换）
      - **修改**：读取 `Spec` 中指定的现有代码文件，生成 diff 修改方案
      - **废弃**：按 `Spec` 与 `Depended By` 定位待删目标及其引用方，生成三步方案：
         1. **解引用**：修改 `Depended By` 中所有引用方，移除对目标代码的引用
         2. **移动**：将目标代码移入项目根目录 `_deprecated/`，并从构建/测试配置中排除（排除结果由用户人工确认）
         3. **索引同步**：同步更新 `planning/architecture.md` 的 `# Dependency Index` 与规格 `Depended By` 字段，
            移除已解引用的引用项，保持与代码一致
         若 `Spec` 未明确指定目标文件/函数，醒示用户确认操作对象，禁止自行搜索删除

   d. **展示 diff 预览**：输出代码差异，等待用户确认。用户提出修改意见 → 回到 c 修订。确认后写入源文件。
       写入后标记状态为 `[新增: 已实现]` / `[修改: 已实现]`（`[废弃]` 标记 `[废弃: 已解引用]`），
       将引用方文件、目标代码原始路径与 `_deprecated/` 内移动后文件路径追加写入 `Affected Files`

   e. **[人工] 测试执行**（仅在 spec 的 `Test Cases` 含 `[人工]` 条目时触发）：
      - 从 spec 的 `Test Cases` 中提取所有 `[人工]` 条目
      - 逐项展示结构化 checklist：操作 / 预期 / 通过标准
      - 提示用户执行并反馈结果（PASS/FAIL）
      - ALL PASS → 进入步骤 f
      - ANY FAIL → 状态更新为 `[新增: 待修复]` / `[修改: 待修复]` / `[废弃: 待修复]`，Issues 写入失败项详情（含用户反馈），
        递增 Retry Count，醒示用户「人工测试未通过，已标记为待修复」，**立即停止**

   f. **调用 /test-verify**（GREEN 验证上下文，测试 `[自动化]` 用例）：
       - 新增/修改：PASS → test-verify 更新状态为 `[已测试]`，清空 `Issues`，重置 `Retry Count`。继续下一个 spec
       - 新增/修改：FAIL → test-verify 更新状态为 `[待修复]`，写入 `Issues`，递增 `Retry Count`。
         code-generate 收到结果后**立即停止**，不继续后续 spec。
         醒示用户「自动化测试未通过，已标记为待修复。请重新运行 `/code-generate`」
       - 废弃：test-verify 执行验证清单（定向测试 + 全量构建 + grep 引用扫描）。
         PASS → 保持 `[废弃: 已解引用]`；FAIL → `[废弃: 待修复]`，写入 `Issues` 并递增 `Retry Count`，
         醒示用户「解引用验证未通过，请根据 Issues 修复受影响模块后重新运行 `/code-generate`」

### 待修复规格的处理

对于 `[新增: 待修复]`、`[修改: 待修复]` 或 `[废弃: 待修复]` 规格：
- 先读取 `Issues` 了解失败原因（含 `[人工]`、`[自动化]` 测试失败详情，或解引用验证失败详情）
- 定位对应的源文件（从 `Affected Files` 获取）
- 分析失败原因 → 修复代码（废弃：修复受影响模块引用后重新解引用，必要时从 `_deprecated/` 移回目标代码）
- 重新执行步骤 e/f（`[人工]` + `[自动化]` 验证）
- 全部 PASS 后清空 `Issues`，重置 `Retry Count`，状态更新为 `[已测试]`（废弃规格保持 `[废弃: 已解引用]`）

### 共识要求

- Agent 自主完成代码生成，但禁止在用户确认前写入文件
- 每个 spec 生成前必须先意图说明实现逻辑，用户确认后再展示 diff
- 涉及多个文件的修改/废弃操作，主动说明各文件影响
- 用户提出调整时修订后重新确认

## 实现约束

- 只允许实现 specifications.md 中当前状态的规格（新增/修改 `[测试已生成]` / `[待修复]`；废弃 `[待删除]` / `[待修复]`）
- 不允许新增未定义规格
- 必须严格遵循 spec 的 `Interface` 字段（公共接口契约）
- 必须使该 spec 的 `[自动化]` 测试全部通过，并引导用户完成 `[人工]` 测试
- 必须处理基础边界情况
- 不允许修改无关文件
- 代码风格必须遵循 `style_guide.md`
- 修改操作必须先读取现有代码文件
- 废弃操作必须确认无其他模块依赖
- 废弃规格必须按 `Depended By` 解引用后移入 `_deprecated/`，禁止直接删除目标代码
- 废弃规格移动后必须请用户人工确认 `_deprecated/` 已从构建/测试配置中排除（不做自动探测）

## 输入来源

本命令的输入从上游文档读取，无需额外 JSON 输入。

### 上游文档

| 文件 | 用途 | 关键内容 |
|------|------|---------|
| `./style_guide.md` | 代码风格规范 | 读取完整文件内容。首次执行时若不存在，调用 `style-resolver` skill 自动生成 |
| `planning/specifications.md` | 实现规格 | 筛选 `[新增: 测试已生成]`、`[修改: 测试已生成]`、`[废弃: 待删除]`、`[新增: 待修复]`、`[修改: 待修复]`、`[废弃: 待修复]` 状态的规格。提取 `Interface`、`Spec`、`Test Double`（如有）、`Test Cases`、`Affected Files`、`Depended By`（废弃规格）。`[待修复]` 时额外读取 `Issues`、`Retry Count` |
| `planning/requirement.md` | 需求背景 | `# Goal`、`# Scope` 章节，作为代码实现的上下文参考 |

### 状态过滤

忽略终态规格（`[新增: 已验证]`、`[修改: 已验证]`、`[废弃: 已删除]`）及未就绪规格（`[新增: 已定义]`、`[修改: 已定义]`、`[废弃: 已解引用]`）。

仅处理 `[新增: 测试已生成]`、`[修改: 测试已生成]`、`[废弃: 待删除]`、`[新增: 待修复]`、`[修改: 待修复]`、`[废弃: 待修复]` 状态的规格。

### 处理顺序

仅处理当前活跃 task 下的规格。按 `planning/specifications.md` 中该 task 的规格从上到下顺序依次处理。

**垂直切片模式**：每个 spec 完整走完「读测试 → 解释逻辑 → 实现 → `[人工]` 验证 → `/test-verify` 自动化验证」后，再处理下一个 spec。任一 spec 验证 FAIL 时立即停止，不继续后续 spec。

当前活跃 task = `planning/tasks.md` 中首个标题标记为 `[DEFINED]` 的任务。若不存在 DEFINED 任务，提醒用户先运行 `/specification-define`。

### 上游文档解析提示

- 规格的 `Interface` 为函数签名/API 端点/类型定义，是实现的精确契约
- 规格的 `Test Double` 字段（如有）由 specification-define 定义，test-generate 生成其实现代码。code-generate 据此生成生产实现（二者共享 Interface）
- 规格的 `Test Cases` 为行为验证场景，agent 需读取测试代码对照 `[自动化]` 条目；`[人工]` 条目在步骤 e 引导用户执行
- 规格状态标记位于章节标题：`## [新增: 测试已生成] name`、`## [修改: 测试已生成] name`
- `Affected Files` 中的测试文件路径和 Test Double 文件路径由 test-generate 写入，源文件路径由本命令追加。废弃规格无测试文件，`Affected Files` 为引用方文件、目标代码原始路径与移动后 `_deprecated/` 内文件路径

## 输出

命令执行后为 `[测试已生成]` 或 `[待修复]` 规格生成/修改实现代码，通过全部验证（`[人工]` + `[自动化]`）后，由 test-verify 更新状态为 `[已测试]`。

## 下一步

- 所有 spec 实现完成（新增/修改状态 `[已测试]`，废弃状态 `[废弃: 已解引用]`）→ 提醒用户运行 `/code-review`
- 存在 `[待修复]` → 用户重新运行 `/code-generate` 根据 Issues 修复代码

## 约束

- 不允许跨规格实现
- 不允许跳过依赖规格
- 不允许生成伪代码
- 不允许在未读测试代码的情况下生成实现
- 任何 spec FAIL 时立即停止，不自动重试，不处理后续 spec
- 修改操作必须先读取现有代码文件
- 废弃操作必须确认无其他模块依赖
- 若 spec 声明了 Test Double → 必须同时生成生产实现，不可仅依赖 Test Double
- Interface 是唯一真相源，Test Double 和生产实现共享此契约
- `[人工]` 测试 ALL PASS 后才可进入 `/test-verify`
- `[人工]` 测试 FAIL 时不可跳过，必须标记 `[待修复]` 并停止
