## 功能说明

该命令取代原 requirement-define / architecture-design / task-breakdown 三个命令，是规划侧的唯一入口。

规划不再是一条固定链（需求 → 架构 → 任务 → 规格），而是一张**计划图**：节点是工作项（带依赖边与失败路由），结构由证据和复杂度决定，规格由 `/specify` 在执行前按需展开（lazy）。两种模式：

- **模式 A（新轮次）**：苏格拉底四问 → 代码探索（自做或委托 explorer 子 agent）→ 复杂度评估 → 产出计划图 `planning/plan.md` → 整体确认
- **模式 B（修订计划）**：变更分类 → 影响推导 → 局部失效 → 确认（取代旧回滚协议的上游修订场景）

设计依据见 `AFTERREAD.md`（四篇论文考察）：静态全量分解有害（级联重执行 +80.5% 成本）；失败恢复的收益来自显式路由而非回滚（去掉回滚性能几乎不变，去掉失败路由明显下降）；规划结构应由证据授权而非预设（证据条件化简约）；简单任务塌缩为链是设计而非退化。

## 行为规则

### 模式 A — 开启新轮次

执行流程：

0. 检查项目根目录 `AGENTS.md` 已包含完整 8 节工作流共识；若缺失或不全，醒示用户先运行 `/setup` 初始化并终止
1. **苏格拉底四问**（对话式追问，不设「澄清探询→起草」仪式，覆盖即止）：
   - 为什么：这个变更要解决什么问题？不做的代价是什么？
   - 隐含假设：需求默认了哪些前提？哪些前提可被推翻？
   - 替代方案：还有哪些实现路径？为什么选当前这个？
   - 边界条件：输入/输出/环境的边界？失败场景有哪些？
   需求要点（`# Goal` / `# Scope` / `# Constraints`）随对话收敛；无法当场关闭的问题记入计划图需求节点的「未决」区
2. **代码探索**（自做或委托 explorer 子 agent，规划 agent 全权裁量）：
   - **自做**：三跳缩小定位（文件树 → 可疑文件 → 相关元素）
   - **委托**：派生 explorer 子 agent（`agents/explorer.md`，只读、上下文隔离；opencode 经 `task` 工具以 `subagent_type: explorer` 调用），传入探索 brief：需求要点摘录 + 目标区域/入口猜测 + 待回答问题清单（2–5 条）+ 负证据（如有）。可按新 brief 多次派生，每次派生无状态（新会话）
   - 适用情形（参考，非强制）：目标区域不清、涉及多模块、引用/调用链需 grep 实测，或仓库较大时内联探索会污染规划上下文
   - 返回的证据摘要（事实 file:line + 可行动洞察 + 未确认项）由规划 agent 消化；探索原始输出永远**用完即弃，不写入计划文档**
   - 未确认项：规划 agent 决定记入需求节点「未决」区或直接向用户追问
   - 规划 agent **不接受** explorer 产出的工作项、复杂度结论或计划图结构——裁决权全在规划 agent
   - 兜底：harness 不支持子 agent 派生（或 explorer 未安装）→ 回退为自做三跳探索
   - 探索深度与复杂度成正比；minimal 级别可跳过大部分探索
3. **复杂度评估**：按 §复杂度评估 判定 `minimal` / `task` / `full`
4. **产出计划图**（单次综合调用）：
   - 需求节点 + 工作项表（变更类型 / 描述 / Depends On / Affects / 设计引用 / 失败路由）
   - full 复杂度 → 附加设计节点（影响分析 + Test Double 策略），单独展示供用户拍板
5. **整体确认**（一个确认点）：展示完整 `planning/plan.md` 预览，用户确认后写入
6. 提醒用户运行 `/specify` 展开第一个活跃工作项

### 模式 B — 修订现有计划

触发场景：需求变化、设计缺陷暴露、`[规格缺陷]` 跨多个工作项、用户要求调整。

执行流程：

1. **变更分类**：将修订内容按 §变更分类规则表 归类
2. **影响推导**：沿依赖边 + 影响规则推导受影响工作项集（确定性推导，非自由发挥）；需要代码级事实（引用位置 grep 实测、跨模块依赖）时可派生 explorer（同模式 A 的机制与 brief 格式，问题清单为影响面问题）
3. **分级处理**：按 AGENTS.md §统一失效协议（DONE 无重叠不动 / TODO 直接改图 / ACTIVE 失效重置并标记「待重做」）
4. **负证据**：失效原因记入计划图「负证据」区（失败转移不得原样重选）
5. 展示修订提案（含失效清单与重做清单）→ 确认 → 写入 `planning/plan.md`，必要时同步 `planning/specs.md`

## 复杂度评估（证据条件化简约）

| 级别 | 判定信号 | 图形态 |
| ------ | --------- | -------- |
| **minimal** | 单文件、纯内部实现、无开放边界、无 API/数据结构变更 | 需求 + 1~2 工作项，无设计层 |
| **task** | 多文件但单模块、无 API 签名变更 | 需求 + 工作项（每项内嵌一句话设计） |
| **full** | 跨模块 / API 签名变更 / 数据结构变更 / 开放边界 / 多方案选型 | 需求 + 设计节点（影响分析 + Test Double 策略）+ 工作项 |

- 默认从最简骨架出发，**仅证据授权升级**；禁止在证据不足时强行升 full
- `minimal` 是流程层概念（省设计节点），`轻量 spec` 是文档层概念（省 Interface 字段，见 AGENTS.md §轻量 spec 规则）——二者正交，可叠加

## 变更分类规则表

工作项类型从小集合中选择，影响规则据此确定性推导；**验证深度**供执行侧（/execute §分层验证）引用：

| 变更类型 | 影响规则 | 验证深度 |
| --------- | --------- | -------- |
| 内部实现 | 局部化：Affects = 所在文件 + 直接调用方（逃逸语义由 agent 判断） | L1-2 |
| API 签名变更 | Affects = 调用方 + 覆写层次 + 依赖文件 | L1-3 |
| 数据结构变更 | Affects = 读写方 + 持久化 + 序列化 | L1-3 |
| 纯新增 | Affects = 新文件 + 接入点 | L1-2 |
| 纯删除/废弃 | Affects = 引用方（以 grep 实测为准） | L1-3（含 grep 扫描） |
| 文档/配置 | Affects = 相应文件 | 轻量 L1 |

## 计划图文档规范（planning/plan.md）

```yaml
---
round: YYYYMMDD-HHMM        # 系统时间戳
baseline: <git HEAD>        # git rev-parse HEAD；非 git 仓库为 none
change_type: feature|enhancement|refactor|bugfix|removal|chore|docs
complexity: minimal|task|full
---
# Goal
# Scope
# Constraints
# 需求节点
- 描述: <需求要义>
- 未决: <条目> — 全部需标记 [resolved] 或 [won't-fix] 方可判定完成
# 工作项
| ID | 变更类型 | 描述 | Depends On | Affects | 设计引用 | 状态 |
| W1 | 内部实现 | 修改订单状态机 | — | order.py | — | TODO |
| W2 | 纯新增 | 邮件通知 | W1 | notify.py | D1 | TODO |
# 设计节点（仅 full 复杂度）
D1: 邮件通知 — 开放边界(SMTP) → Test Double: FakeMailer(内存数组)；影响: W1 调用方
# 失败路由（默认三分类见 AGENTS.md §失败路由协议；个别工作项可覆盖）
- W3: [实现缺陷]→先检查上游 W2 是否 API 签名变更（表面报错点≠根因点）
# 延后工作（运行时分解——执行中发现的新工作项登记于此，经 /specify 展开）
- W4: <发现时补充登记>
# 负证据（失败转移不得原样重选；Attempt Log 升级 L3 时精华汇总于此）
- W2: 曾采用 Stub 方案失败（原因…），不得原样重试
```

要点：

- **工作项状态三态**：`TODO`（未展开规格）→ `ACTIVE`（规格已定义或执行中）→ `DONE`（该工作项全部规格终态）；细节状态由规格状态机承载（AGENTS.md §状态机与记法规范）
- **活跃工作项** = 首个「Depends On 全部 DONE」的 TODO/ACTIVE 工作项
- **边双轨**：Depends On 承载 ON-SUCCESS 先决拓扑；失败路由承载 ON-FAILURE——「失败后下一步去哪」是显式图操作
- 不设模块级 Dependency Index：废弃引用与影响面以 grep 实测为准
- 探索原始输出（工具输出、中间推理）禁止写入本文档；只写证据摘要与决策

## 输出

- 模式 A：写入 `planning/plan.md`（新轮次计划图）
- 模式 B：更新 `planning/plan.md`（修订/失效/负证据），必要时同步 `planning/specs.md` 规格状态

## 下一步

- 模式 A 确认后 → 提醒用户运行 `/specify` 展开首个活跃工作项
- 模式 B 修订后 → 失效工作项按 §统一失效协议 进入重做（规格重定义走 `/specify`，代码修复走 `/execute`）

## 约束

- explorer 子 agent 只读（无写文件与嵌套派生权限，bash 仅限只读命令），仅返回证据摘要；规划 agent 不接受其工作项、复杂度结论或计划图结构
- 禁止在证据不足时强行升级复杂度（默认最简骨架）
- 禁止在规划阶段一次性产出全部规格（规格由 `/specify` 按需展开）
- 禁止把探索原始输出写入计划文档（scratch 用完即弃）
- 变更类型必须从规则表选择，影响推导必须基于规则而非自由发挥
- 工作项必须成图：依赖无环、引用闭合，新增工作项必须登记 Depends On
- DONE 且文件无重叠的工作项不得因无关修订自动失效（重叠守卫，见 AGENTS.md §统一失效协议）
- 写文件前必须展示预览并等待用户确认
- 需求节点的未决问题未全部关闭前，不得判定轮次可收尾（wrap-up 依赖此判定）
